# HUF Knowledge Backend Contract

This document describes how to add a new knowledge storage backend to HUF, either as a built-in backend or as an external Frappe app plugin.

## What is a knowledge backend?

A knowledge backend stores and retrieves text chunks for HUF's RAG (Retrieval-Augmented Generation) system. Each `Knowledge Source` DocType selects a `knowledge_type` (e.g. `sqlite_fts`, `pgvector`, `chroma`) and the backend provides the actual storage, indexing, and search implementation.

## The `KnowledgeBackend` contract

Every backend must subclass `huf.ai.knowledge.backends.KnowledgeBackend` and implement the following abstract methods:

| Method | Purpose |
|--------|---------|
| `initialize(self, knowledge_source: str, config: dict) -> None` | Prepare the store for the given source name. `config` is built by `_build_backend_config()` in `huf/ai/knowledge/indexer.py` and contains the DocType's generic fields plus merged `advanced_config` values. |
| `add_chunks(self, chunks: list[dict]) -> int` | Index a list of chunks. Returns the number of chunks added. Embeddings are **always generated by HUF** before this call (see implementation paths below). |
| `delete_chunks(self, input_id: str) -> int` | Delete every chunk belonging to a single `Knowledge Input`. Returns the number of chunks removed. |
| `search(self, query: str, top_k: int = 5, filters: dict \| None = None) -> list[ChunkResult]` | Return the most relevant chunks for `query`. For vector backends this receives an embedding via HUF's embedding module before searching. |
| `clear(self) -> None` | Remove every chunk for this knowledge source. |
| `get_stats(self) -> dict` | Return runtime statistics such as `chunk_count`, `backend_type`, and store health. |

Optional hooks and helpers that backends may override:

| Method / Attribute | Purpose |
|--------------------|---------|
| `get_advanced_config_schema(cls) -> list[dict]` | Declare backend-specific tuning parameters that appear in the Desk UI under **Advanced Configuration**. See schema format below. |
| `health_check(self) -> tuple[bool, str]` | Built into `LlamaIndexBackend`; custom backends may add their own. |
| `supports_filters(self) -> bool` | Declare whether the backend supports metadata filters. |
| `supports_hybrid_search(self) -> bool` | Declare whether the backend supports hybrid (keyword + vector) search. |

### `ChunkResult`

`search()` must return a list of `ChunkResult` objects:

```python
@dataclass
class ChunkResult:
    chunk_id: str
    text: str
    title: str | None = None
    score: float = 0.0
    source: str | None = None
    metadata: dict[str, Any] | None = None
```

### `get_advanced_config_schema` format

```python
@classmethod
def get_advanced_config_schema(cls) -> list[dict[str, Any]]:

        },
        {
            "key": "hybrid_search",

            "type": "boolean",
            "default": False,

        },
```

Supported field types: `number`, `text`, `boolean`, `select`. Use `visible_when: {field: value}` to conditionally show fields based on other advanced config values or first-class DocType fields.

## Two implementation paths

HUF supports two ways to implement a backend. Choose the one that matches your store.

### Path 1: subclass `LlamaIndexBackend` (recommended for LlamaIndex-supported stores)

Use this for any vector store that has a LlamaIndex adapter (Chroma, PGVector, Weaviate, Qdrant, Milvus, etc.).

HUF handles:

* chunk-to-`Document` conversion,
* HUF-side embedding generation,
* `VectorStoreQuery` search plumbing,
* normalizing results to `ChunkResult`.

Your subclass only supplies:

* `_validate_config()` – validate connection settings from `config`,
* `_create_vector_store()` – return the LlamaIndex `VectorStore` instance,
* optional metadata-filter scoping via `_build_search_filters()`,
* optional `get_advanced_config_schema()` for tuning parameters.

Example skeleton:

```python
from typing import Any

from huf.ai.knowledge.backends.llamaindex_base import LlamaIndexBackend

class QdrantBackend(LlamaIndexBackend):
    _backend_type = "qdrant"

    def _validate_config(self) -> None:
        if not self.config.get("qdrant_host"):
            frappe.throw("qdrant_host is required")

    def _create_vector_store(self) -> Any:
        from llama_index.vector_stores.qdrant import QdrantVectorStore

        return QdrantVectorStore(
            collection_name=self.knowledge_source,
            host=self.config["qdrant_host"],
            port=self.config.get("qdrant_port", 6333),
            # ...
        )

    @classmethod
    def get_advanced_config_schema(cls) -> list[dict[str, Any]]:
        return [
            {
                "key": "prefer_grpc",
                "label": "Use gRPC",
                "type": "boolean",
                "default": False,
                "help_text": "Connect to Qdrant over gRPC instead of HTTP.",
            },
        ]
```

A real backend is typically **50–100 lines** when it builds on `LlamaIndexBackend`.

### Path 2: implement `KnowledgeBackend` directly (portable or unsupported stores)

Use this when LlamaIndex does not support your store, when you want zero extra dependencies, or when you need full control over SQL/queries.

You are responsible for:

* generating embeddings via `huf.ai.knowledge.embedding.get_embedding[s]`,
* storing chunks and embeddings,
* executing search queries,
* returning normalized `ChunkResult` objects.

The built-in `sqlite_fts` and `sqlite_vec` backends follow this path. The `sqlite_vec` backend, for example, creates its own SQLite tables, runs raw `vec0` SQL queries, and calls HUF's embedding module directly.

Example skeleton:

```python
import frappe
from huf.ai.knowledge.backends import ChunkResult, KnowledgeBackend

class MyPortableBackend(KnowledgeBackend):
    def initialize(self, knowledge_source: str, config: dict[str, Any]) -> None:
        self.knowledge_source = knowledge_source
        self.config = config
        # open connection / create tables

    def add_chunks(self, chunks: list[dict[str, Any]]) -> int:
        from huf.ai.knowledge.embedding import get_embeddings, resolve_embedding_config

        texts = [c["text"] for c in chunks]
        embed_config = resolve_embedding_config(self.knowledge_source)
        embeddings = get_embeddings(texts=texts, model=embed_config["model"], api_key=embed_config.get("api_key"))
        # store chunks + embeddings
        return len(chunks)

    def search(self, query: str, top_k: int = 5, filters: dict[str, Any] | None = None) -> list[ChunkResult]:
        from huf.ai.knowledge.embedding import get_embedding, resolve_embedding_config

        embed_config = resolve_embedding_config(self.knowledge_source)
        query_embedding = get_embedding(text=query, model=embed_config["model"], api_key=embed_config.get("api_key"))
        # run similarity search
        return [ChunkResult(chunk_id="1", text="...", score=0.9)]

    # ... delete_chunks, clear, get_stats
```

## Embeddings are always HUF-side

Regardless of the path, embeddings are generated by HUF before chunks reach the backend. Do **not** configure the store to compute its own embeddings. This keeps backends interchangeable and ensures cost/auditing stays in HUF.

Use:

```python
from huf.ai.knowledge.embedding import get_embedding, get_embeddings, resolve_embedding_config
```

## Core connection fields vs. `advanced_config` tuning params

`Knowledge Source` has a fixed set of first-class DocType fields. Built-in backends such as `pgvector` and `chroma` have dedicated fields for host, port, SSL, database, etc.

**External apps cannot add new first-class DocType fields without patching HUF.** Therefore, the plugin convention is:

* Put **backend-specific connection settings** (host, port, API key, collection name, etc.) in `advanced_config`.
* Use the generic vector settings that already exist on the DocType: `embedding_model`, `vector_dimension`, `embedding_provider`, `chunk_size`, `chunk_overlap`.
* Use `get_advanced_config_schema()` to expose those connection and tuning params in the Desk UI.

Guidance:

| Concern | Where to declare |
|---------|------------------|
| How to reach the store (host, port, URL, credentials, SSL) | `advanced_config` schema |
| Index/search tuning (HNSW params, tokenizers, distance metric) | `advanced_config` schema |
| Embedding model, dimension, provider | Existing DocType fields |
| Chunk size / overlap | Existing DocType fields |

The `_build_backend_config()` merger in `huf/ai/knowledge/indexer.py` passes the merged first-class fields and `advanced_config` into `backend.initialize(config)` as a single flat dict, so backends read `config["my_param"]` directly.

## Registering an external backend via `huf_knowledge_backends`

External Frappe apps register backends through a hook, exactly like HUF's `huf_tools` hook for agent tools.

In your external app's `hooks.py`:

```python
huf_knowledge_backends = {
    "qdrant": "my_app.knowledge.qdrant_backend.QdrantBackend",
}
```

Multiple backends can be registered in the same dict:

```python
huf_knowledge_backends = {
    "qdrant": "my_app.knowledge.qdrant_backend.QdrantBackend",
    "weaviate": "my_app.knowledge.weaviate_backend.WeaviateBackend",
}
```

### Validation rules

* The class must be importable.
* The class must subclass `KnowledgeBackend`.
* Hook-provided type keys **cannot override built-in backends** (`sqlite_fts`, `sqlite_vec`, `chroma`, `pgvector`, `zvec`, `weaviate`). Collisions are skipped and logged as a warning.
* Duplicate type keys across apps keep the first registration encountered and warn on subsequent ones.
* Malformed hook entries (non-dict values) are skipped with a warning.

> **Frappe hook-merge note:** Frappe merges dict-valued hooks across declarations
> into a single dict whose values are *lists* (`{"qdrant": ["path.to.Class", ...]}`).
> The registry normalises this internally and the **first declaration for a type
> key wins** — within one app and across apps. Declare each backend type at most
> once per app; do not rely on later entries overriding earlier ones.

Once registered, the backend is immediately usable from the `Knowledge Source` DocType and from `get_advanced_config_schema()` through the whitelisted API.

## Live-test bar for new backends

Before a new backend is considered production-ready, it must pass:

1. **Import and contract tests** – class resolves through `get_backend(type_key)`, subclasses `KnowledgeBackend`, and implements all abstract methods.
2. **Schema round-trip** – `get_advanced_config_schema(type_key)` returns valid schema entries via the whitelisted API.
3. **Index / search cycle** – create a temporary `Knowledge Source`, index a few chunks, search with a related query, and verify non-empty `ChunkResult` with sensible scores.
4. **Delete / clear cycle** – `delete_chunks(input_id)` removes the right chunks; `clear()` empties the store.
5. **Stats / health** – `get_stats()` returns expected metadata and `health_check()` (if implemented) reports healthy after initialization.
6. **No backend-generated embeddings** – verify the backend consumes HUF-generated embeddings and does not call its own embedding model.
7. **Ruff clean** – touched files pass `ruff check` and `ruff format`.
